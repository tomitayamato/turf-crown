# 三冠への道 ─ TURF CROWN

スマホ縦持ちの競馬育成ゲーム。一頭の馬を育て、春の早月賞・初夏の日本クラウン・秋の菊華賞に挑みます。
外部ライブラリなし、ゲーム本体は `index.html` 1ファイルです。

## 遊ぶ

**→ https://tomitayamato.github.io/turf-crown/**

スマホのブラウザで開き、ホーム画面に追加すると全画面のアプリとして動きます。

> **`index.html` をダブルクリックしても音が鳴りません。**
> BGMを `audio/*.wav` の別ファイルにしたので、`file://` で開くと
> ブラウザの制限（CORS）で読み込めません。手元で動かすときはサーバー経由にしてください。
>
> ```
> cd このフォルダ && python3 -m http.server 8000
> # → http://localhost:8000/
> ```

## 中身

`index.html` の `<script>` 内は4つのブロックに分かれています。

| ブロック | 内容 |
|---|---|
| データ定義 | コース・脚質・ハイアンドロー配点・ライバル強度・馬名プール（135頭） |
| レースシミュレーション | コース地点の前計算、物理モデル、ライバル生成、オッズ |
| ゲーム進行とUI | 画面遷移、育成、振り分け、出走表、リザルト、殿堂 |
| コース描画・レース再生 | コース全体図、高低差ガイド、走路（追尾カメラ）、実況、再生ループ |

## レース名（すべて仮・あとで差し替え可）

| ゲーム内 | 読み | 実在の対応 | 競馬場・距離 |
|---|---|---|---|
| 早月賞 | さつきしょう | 皐月賞 | 中山 芝2000m 右回り内回り／直線310m・急坂2回 |
| 日本クラウン | にっぽんクラウン | 日本ダービー | 東京 芝2400m 左回り／直線526m・残り460mから上り |
| 菊華賞 | きっかしょう | 菊花賞 | 京都 芝3000m 右回り外回り／坂を2回越える |
| 有真記念 | ありまきねん | 有馬記念 | 中山 芝2500m 右回り内回り／コーナー6回・急坂2回 |

読みは `YOMI` に登録してあります。造語なので読み上げ側の辞書には載っておらず、
放っておくと「そうげつしょう」「にほんクラウン」のように読まれます。
いまの実況文にレース名は入っていないため**音としては出てきません**が、
あとで読ませたくなったときのための保険です。

**競馬場名は実名**（中山・東京・京都）です。競馬場名は市販の競馬ゲームでも一般的に
実名で使われています。一方で**レース名（皐月賞・日本ダービー・菊花賞・有馬記念）は
JRAの登録商標**なので仮の名前にしてあります。アプリとして公開する際も、
この線引き（競馬場＝実名／レース名＝仮名／馬名＝架空／団体名＝架空）を保つのが安全です。

同じ理由で、馬券の透かしと発売所に入れていた **JRA は TRC に差し替えました**
（ゲームタイトル TURF CROWN から取った架空の略称）。競馬場名や馬名のもじりは
「実在のものに言及している」だけですが、JRA は団体そのものを指す登録商標で、
しかも透かしはロゴの意匠を模すことになります。ゲーム内の小道具としての表示は
一般に商標的使用にあたらないと整理されますが、ストアのスクリーンショットに映ると
「公認アプリ」と誤認される余地が生まれるため、リリースを見据えて外してあります。
券面の質は落ちていません。効いているのは三列構成・太ゴシック・生成りの紙・
水色の帯であって、文字列そのものではないためです。

名前は `COURSES` の `name` / `track` を書き換えるだけで変更できます。
高低差とコーナー位置は実際のコースを再現しており、勝ちタイムも実際の記録帯に一致します。

| レース | ゲームの勝ちタイム | 実際の勝ちタイム帯 |
|---|---|---|
| 早月賞（中山2000） | 約 2:00 | 1:57〜2:00 |
| 日本クラウン（東京2400） | 約 2:24 | 2:22〜2:26 |
| 菊華賞（京都3000） | 約 3:02 | 3:01〜3:06 |
| 有真記念（中山2500） | 約 2:31 | 2:30〜2:33 |

## タイトル画面

起動時は**タイトル画像＋TAP TO START**のスプラッシュです。画面のどこをタップしても
馬選択へ進みます。下部の「殿堂入り」「遊びかた」はタップを伝播させないので、
そちらを押してもゲームは始まりません。

ロゴは「TURF CROWN」、その上に「三冠への道」。
**2026年11月7日に `タイトル画像261106.png`（940×1672）へ差し替えました。**
ロゴ・紋章・金の枠まで含んだ一枚絵なので、画面側は背景に敷くだけです。
（それ以前は `title_source2.jpg` を加工して日本語を描き直したものを使っていました）

- 画像は幅759px・JPEG品質80でbase64埋め込み（215KB→base64で287KB）。1ファイル構成を保つため。
  375ptの端末でちょうど2倍。元のPNG（1.9MB）をそのまま埋めるとページが重くなります
- `background-color` は**画像のいちばん下の行の色**（`#02271e`）に合わせてあります。
  縦に長い端末（375×932 など）では画像の下に余白が出るので、色が違うと横一本の継ぎ目が見えます
- 「TAP TO START」は画像に焼き込まず**CSSアニメーション**（`@keyframes tapPulse`）
- **`background-size:100% auto` ＋ `background-position:center top`** にしています。
  `cover` だと縦長の画面でロゴの左右が切れるためです。下に余る領域は背景色と
  下部のグラデーション（`.splash-foot` の `padding-top`）で継いでいます

画像を差し替えるときは `.splash` の `background-image` の base64 を置き換えて、
`background-color` も新しい画像の最下行の色に合わせ直してください。

## アイコンと PWA（2026年11月7日）

元絵は `アイコン.png`（1254×1254）。**角丸の半径が 20.7% で、iOS がかけるマスク（22.37%）と
ほぼ一致**しているので、iPhone のホーム画面ではそのまま意図どおりに出ます。よく出来ています。

ただしそのままでは2か所で崩れるので、用途別に書き出しました（`icons/`）。

| ファイル | 中身 | 使われる場所 |
|---|---|---|
| `apple-touch-icon.png` 180 | 元絵・角の黒を緑に | iPhone のホーム画面 |
| `icon-192.png` / `icon-512.png` | 同上（`purpose: any`） | PWA 一般・インストール画面 |
| `icon-maskable-512.png` | 紋章だけ（`purpose: maskable`） | Android のホーム画面 |
| `favicon-32.png` / `favicon-16.png` | 紋章だけ・輪なし | ブラウザのタブ |

**直した点1：四隅の黒**
元絵は透過なし（`hasAlpha: no`）で、角丸の外側が**黒で塗られて**います。
iOS はマスクで切り落とすので問題ありませんが、マスクをかけない場所
（タブのアイコン、PC の Chrome のインストール画面、GitHub のプレビュー）では
**黒い角が残ります**。角丸の外側を `#02301f`（絵の下端の緑）で塗り直しました。
iOS のマスクのほうが丸いので、塗った緑は結局切り落とされます。見た目は変わりません。

**直した点2：Android の切り抜きと小さいサイズ**
Android は丸・角丸・雫などに切り抜くので、`maskable` は**中央80%の円の中**に
収まっている必要があります。元絵は「TURF CROWN」が端まで伸びているため、
丸く切ると**両端の文字が切れ、金の枠も消えます**。
また 48px 以下では題字が読めず、16px（タブ）ではただの緑の染みになります。

そこで小さいサイズは**紋章（王冠＋馬蹄）だけ**にしました。
ゲーム本体に残っていた紋章の描画コード（旧 `silkCv`、王冠と馬蹄を canvas で描く部分）を
そのまま使っているので、絵柄は元絵と同じ系統です。16px でも馬蹄と王冠が判別できます。

```
元絵 → 丸に切る → 「URF CROW」になり枠も消える  ✗
紋章 → 丸に切る → そのまま                       ✅
```

**`manifest.webmanifest`**：`display:standalone` ／ `orientation:portrait` ／
`start_url:"./"`・`scope:"./"`（GitHub Pages のサブディレクトリでも動くように相対で書いてある）。
`theme_color` は `index.html` の `<meta name="theme-color">` と同じ `#0d1a14`。

アイコンを作り直すときは、ブラウザの canvas で書き出しています。
手順は `scratchpad/gen.html` と `serve.py` の `/_save/` を参照（サーバに POST して保存する）。

## GitHub で公開するとき

必要なファイルはこれだけです（合計 約21MB）。

```
index.html            588KB   本体（1ファイル）
manifest.webmanifest
icons/                850KB
audio/                 20MB   wav 9本
```

パスはすべて相対なので、`https://tomitayamato.github.io/turf-crown/` のような
サブディレクトリ配信でもそのまま動きます。

**先に `.gitignore` を確認してください。**
フォルダには音源の元データが残っていて、
`【勉強・作業用BGM】….mp3` は **124MB** あります。
GitHub は1ファイル100MBを超えると**push 自体を拒否**するので、
`.gitignore` で root の `*.wav` と `*.mp3` を除外してあります
（`audio/` の中は除外されません）。これで 239MB → 約25MB になります。

GitHub Pages は Settings → Pages → Source を `main` ブランチの `/ (root)` にするだけです。

## レース画面の作り

```
── 早月賞 ──          ← 金のグラデーションの装飾見出し
中山競馬場 芝2000m GI
┌──────────────────────┐
│ 高低差ガイド（コース全体・現在位置つき）│  走路とは独立した参考図。
├──────────────────────┤  走り終えた区間が塗られ、
│ 走路（馬群の周辺だけを映す追尾カメラ）  │  上り坂／下り坂を表示。
└──────────────────────┘
実況テロップ
コース全体図（先頭と自分の位置）
速度切替（標準／2倍速／直線から）
リアルタイム上位5頭＋自分
単勝馬券（自分の馬）          ← 下部の余白を活用
```

最下部には**自分の馬の単勝馬券**を置いています（`renderTicket`）。
実際の勝馬投票券の券面構成をそのまま写した意匠で、横長 1330:797 の比率、
淡い緑の TRC 透かしと水色の縦帯を敷いた生成り色の紙に、三列で刷ります。

```
2026年3回6日 ┃ WIN ┃  ┏━━┓
中 山        ┃     ┃  ┃13┃ ★★★100円
▌11▐レース   ┃ 単  ┃  ┗━━┛
▞▚ ▞▚        ┃     ┃  チュウワウィザー
▚▞ ▚▞        ┃ 勝  ┃
第８６回（GI）┃     ┃
早月賞        ┃     ┃
TRC　中山     ┃ WIN ┃      合計★★★★１枚★★★★１００円
４月１４日    ┗━━━┛  5368758262437 1338227098378 58874606
```

左列が開催回次・競馬場・レース番号・二次元コード・回次と格・レース名・発売所、
中央が式別（単勝）を縦書きで囲んだ枠、右列が馬番と金額・馬名・合計、
最下段が通し番号です。

**券面に載せるのは実券にある情報だけ**にしています。オッズと人気は実券には印字されないので外しました
（どちらもレース前の出走表で確認できます）。馬番も枠色では塗らず、実券どおり白地に黒です。
色を入れると券というより UI パーツに見えてしまうためで、自分の馬の識別は
走路のマーカーと実況テロップが担っています。二次元コードは `fakeQR()` が馬番とコースから生成する飾りで、
実際には読み取れません。開催回次や月日（`TICKET_INFO`）は実際の番組に近い数字を当てています。

券面は実券どおりに保ちたいので、能力値は載せていません
（一時は券の外に添えていましたが、レース中に見るものではないので外しました）。

文字サイズはコンテナクエリ（`#rcTicket{container-type:inline-size}` ＋ `2.88cqw`）で
券の幅に追従させ、全要素を `em` で組んでいます。`cqw` は**自分自身を参照できない**ため、
`container-type` は券ではなく外側の `#rcTicket` に置く必要があります。

走路は**コース全体ではなく馬群の周辺だけ**を映します。2400mを画面幅に収めると
60mの着差が画面の2.5%にしかならず馬群が点になるためです。
先頭を画面の約7割の位置に置くことで、馬群が画面中央寄りに収まります。
映す範囲は馬群の広がりに合わせて自動で伸縮し、**直線に入るとカメラが固定されて
ゴールが右に見え、馬群が左から入ってくる**形になります（`FINAL_SPAN`＝155m）。
ゴール前は再生速度も落として競り合いを見せます（`FINAL_SLOW`）。

マーカーの重なり対策は**馬番ごとの固定オフセット**だけです。毎フレーム押し出す方式は、
競り合うと押す向きが反転してカクついたため使っていません。多少の重なりは許容し、
自分の馬は常に最前面に描きます。

縦方向は**内ラチからの位置どり**です。脚質で定位置が決まり（逃げは内、差しは中〜外）、
器用さが低いほど外を回らされ、前が詰まれば外へ持ち出し、直線では差し馬が外に出します。
見た目は中継のトラッキング表示に寄せ、各馬は枠色のマーカーと速度に応じた軌跡で描いています。

高低差は走路とは切り離したガイドで、馬はその線には沿いません。

**「直線から」は直線に入るまでの一度きり**です（`skipToFinal`）。
以前は何度でも押せて、そのたびに最後の直線へ巻き戻っていました。
レースは一度きりのものなので、押した時点より前には戻らないようにし、
直線に入ったあと・ゴール後はボタン自体を無効にしています。

**先頭が内ラチ沿いを通る規則は、直線に入ったら切ります**（`updateLanes`）。
この規則を最後まで効かせると、外から差してきた馬がゴール板で先頭に立った瞬間に
内へ寄せに行き、**上にいたマーカーが一気に下へ移動して見えます**。
ゴールした馬の進路も、通過した時点で固定します。

勝ち馬が最後の400mで内外に動く量は、修正前が**0.43**（コース幅比・最大0.50）、
修正後は**0.22**（最大0.24）。残っている分は差し馬が直線で外へ持ち出す動きで、これは意図どおりです。

## スマホで1画面に収める

iPhone を前提に、**スクロールなしで全体が見える**ことを目標に各画面を詰めました。
Safari の表示領域はだいたい 740px（iPhone 15 クラス）なので、そこを基準にしています。

| 画面 | 調整前 | 調整後（740px基準） |
|---|---|---|
| タイトル・殿堂 | 収まる | 収まる |
| 馬選択 | 945 | 826 |
| 育成（ハイアンドロー） | 956 | 752 |
| 育成（振り分け） | 1109 | **742 ○** |
| 出走表 | 収まる | **収まる** |
| レース結果 | 787 | **740 ○** |
| 最終リザルト | 1049 | 1015 |

主にやったこと。

- 全体の余白を一段ずつ詰める（カード内 13→11px、画面下 28→16px など）
- 「ROUND 1 / 3」を見出しの副題にまとめ、大きな数字のブロックを廃止
- 振り分け画面の**能力説明文を削除**（同じ説明が馬選択と遊びかたにある）
- のこりポイントと ±1/±5/±10 を**一行**に
- 次走カードを**2行**に（レース名と条件を同じ行に）
- 育成画面の状態パネルを**2列**にして棒グラフを外し、等級と数値だけに
  （馬名は飾り罫つきの金文字で中央に置き、脚質は合計・次走と同じ行へ下げました）
- 馬選択の脚質カードを圧縮（画像152→92px、レーダー158→112px、抽選の説明文を削除）

**どうしても収まらない画面**は、主要ボタンを `position:sticky` で下端に貼り付けました（`.stick`）。
最終リザルトは戦績を全部載せるので必ず溢れますが、「タイトルへ／もう一頭育てる」は
常に押せる位置にあります。レース中の画面も、**馬券を除いた部分（走路・実況・コース図・
速度切替・着順）は693pxに収まる**ので、見るべきものは最初から全部見えています。
馬券だけが下にぶら下がる形です。遊びかたは読み物なので対象外としています。

画面がさらに小さい端末（iPhone SE クラス・667px）では育成画面が80pxほど溢れますが、
貼り付けたボタンのおかげで操作は詰まりません。

## 出走表の画面

レース名はレース画面と同じ飾り罫つきの金文字にして、その下に月・競馬場・距離・格を一行で添えます。
この見出し（`.raceHead`）は**出走表・レース中・レース結果の3画面で共通**です。
同じレースを追っているあいだ見出しが変わらないので、画面が切り替わっても流れが途切れません。

18頭を素のまま並べると表だけで縦に500px以上になり、「レースへ」ボタンまで毎回スクロールが要りました。
いまは**表を枠に収めてスクロール**させ、見出し行は `position:sticky` で上に残します。
これで画面に収まり、コース図もボタンも同時に見えます。

枠の高さは固定せず、**画面の余りをそのまま表に回します**
（`calc(100dvh - 404px)`。404px は見出し・コース図・ボタン・注記の合計）。
`vh` ではなく `dvh` を使うのは、スマホのツールバーを差し引いた実際の高さで測るためです。
740px の端末で336px・9頭ぶん、667px の端末で263px・7頭ぶんが一度に見えます。
レース結果の着順表も同じ考え方で、そちらは上に着順やタイムが載るぶん枠を狭くしています。

**自分の馬が枠の中央に来た位置で開きます**（`prepareRace` 末尾）。
18頭のどこを引いても一度もスクロールせずに自分を確認でき、全馬番で検証済みです。
枠の下端には薄いグラデーションを敷いて、まだ下に続いていることを示しています。

レース結果の着順表も**全18頭**を同じ枠に収めています。以前は上位8頭＋「…」＋自分の行でしたが、
掲示板の外で何が起きたかが見えませんでした。

ただしスクロール位置の初期値は出走表と逆で、**頭から表示します**。
結果表でまず見たいのは勝ち馬だからです。自分が枠の外（おおむね12着以下）にいるときだけ、
届くぶんだけ下に送ります（`scrollRowInto` の第3引数で中央寄せと最小移動を切り替え）。
自分の着順は上の大きな数字がすでに伝えているので、表のほうは上位から読ませるほうが筋が通ります。

## 道中の位置取り

脚質ごとに「このあたりを走る」帯（`STYLES[].band`）があり、そこから外れると
`effort` を補正して戻します。補正は**前に出るときと控えるときで強さが違います**。

| 向き | 係数 | 上限 | 理由 |
|---|---|---|---|
| 前に出る (`K.urge`) | 0.085 | 0.020 | 脚力以上には出られない |
| 控える (`K.holdGain`) | 0.70 | 0.300 (`K.hold`) | 手綱で抑えられるので強く効く |

控えのほうは**序盤だけ強く効かせます**（`K.holdTo=0.18` まで。そこから 0.70 の地点に
かけて 0.085 へ戻す）。これをしないと、能力で出た差をその場で打ち消してしまい、
**コースごとの能力の効き方が消えます**。実測した失敗例：

| 設定 | 日本クラウンの 器用さ | 実測順 |
|---|---|---|
| 抑えなし（旧） | 37% | 走力＞器用さ＞スタミナ＞パワー ✅ |
| 道中ずっと抑える | 20% | 走力＞スタミナ＞パワー＞**器用さ** ✗ |
| 帯の中心まで戻す | 11% | 走力＞スタミナ＞パワー＞**器用さ** ✗ |
| **序盤だけ抑える（採用）** | **31%** | 走力＞器用さ＞スタミナ＞パワー ✅ |

これで**カンストした差し馬**も脚質どおりに走ります（早月賞・各60回の平均順位）。

| 進捗 | 15% | 35% | 55% | 75% | 90% |
|---|---|---|---|---|---|
| 旧 | 1.2 | 2.4 | 1.0 | 1.0 | 1.0 |
| 新 | 8.7 | 8.4 | 3.4 | 2.0 | 1.0 |

脚質ごとの勝率は動いていません（逃げ88% / 先行82% / 差し87%、早月賞・各300回）。
ただし全体の難度は少し上がりました。抑えられた馬は脚をためて終いが伸びるので、
**相手の差し馬が以前より怖くなります**（日本クラウンの走力型で 62% → 50%）。

## 単勝オッズ

能力を `exp((v-mean)/9)` で確率に変える形ですが、素のままだと**カンストした馬が1頭いると
他の17頭の確率が1000万分の1まで潰れ、全頭が上限の999.0に張り付きます**。
`ODDS_Z0`（1.5）までは素通しし、そこから `ODDS_ZC`（3.2）へ `tanh` でなめらかに
頭打ちさせています。ふつうの馬群は ±1.8 程度に収まるので、通常のレースは変わりません。

| 自馬 | 修正前 | 修正後 |
|---|---|---|
| カンスト | 1.1 ／ 他17頭すべて 999.0 | 1.3 ／ 他馬 6.2〜222.8 |
| ふつう | 1.8 ／ 6.1〜108.4 | 変わらず |

## BGM の切り替え（2026年11月7日）

スマホで遊ぶと「前の画面のBGMが少し残る」という指摘があり、音源の帯域を 500KB/s に
絞って測ったところ、**前の曲が数秒そのまま鳴り続けていました**。

| 画面の切り替え | 直す前 | 直した後 |
|---|---|---|
| タイトル → 脚質選択 | 11.4s（初回の実測） | 同じ（初回は取りに行くしかない） |
| 育成（ハイアンドロー） | 3.4s | 3.4s → 以降は **0.00s** |
| 出走表（ファンファーレ） | 3.0s | **0.00s** |
| レース | 6.3s | **0.00s** |
| 結果 | 5.7s | **0.00s** |
| 2周目の育成 | 3.4s（毎回ダウンロードし直し） | **0.00s** |

原因は3つありました。

**1. 読み終わるまで前の曲を落としていなかった。** `play()` は音源を取りに行き、
デコードが終わってから `_start()` で前の曲をフェードさせていました。
回線が細い端末ではその間ずっと前の画面の曲が**音量そのまま**で鳴り続けます。
いまは、手元に音源がない場合はその場で 0.8 秒かけて落とします。

**2. デコード済みを3本しか持っていなかった。** 一周で使う曲は
育成中・ハイアンドロー・ファンファーレ・レース中・空気感・歓声・リザルトの**7本**で、
3枠を奪い合うので**画面を変えるたびに必ず再ダウンロード**になっていました。
本数ではなくバイトで見るようにして、上限を 36MB にしています。
デコードすると AudioContext の 44.1kHz に伸びるため、32kHz の音源でも1.4倍に膨らみます。

| 音源 | ファイル | デコード後 |
|---|---|---|
| 育成中 | 5.8MB | 16.1MB |
| 空気感 | 3.9MB | 10.7MB |
| レース中 | 3.2MB | 8.5MB |
| リザルト | 2.9MB | 7.5MB |
| ゴール歓声 | 1.9MB | 5.1MB |
| ハイアンドロー | 1.7MB | 4.4MB |
| ファンファーレ | 1.5MB | 4.0MB |

いちばん重なるのはレース中（空気感＋レース中＋歓声＋先読みしたリザルト＝**35.0MB**）です。
実測でこの4本が同時に残ることを確認しました。28MB にしていたときは歓声が追い出されます。

**3. 次に要る曲を先に取っていなかった。** `BGM_NEXT` を足して、いまの画面にいるあいだに
次の画面の曲を**1本ずつ順番に**取っておきます（`queuePreload` / `_pump`）。
いま鳴らす曲の読み込み中は待ち、回線を取り合わないようにしてあります。
ゴール歓声の先読みも同じ列に乗せました。

```
title → []            select/hall/howto → [hl]
train → [fanfare, race, air]              entry → [race, air, result]
race  → [result]      rres/result → [hl]
```

おまけで、同じ曲を取りに行っている最中にもう一度 `play()` が呼ばれると
**同じ曲が二重に立ち上がって**いました（起動直後に3本重なります）。`_loading` で止めています。

**測り方**：`scratchpad/serve.py` が `kbps.txt` を読んで `.wav` だけ帯域を絞ります。
数字を書き換えればサーバを止めずに回線を変えられます。
ブラウザのHTTPキャッシュが効くと一瞬で終わってしまうので、**初回の数字で判断してください**。

## BGM

5曲＋効果音4本を画面ごとに鳴らし分けます。音源は **32kHz モノラル WAV** にして
`audio/` に**別ファイルで置き**、`fetchBuf()` が XHR で取りに行きます
（`BGM_SRC`。合計約20MB、index.html 本体は0.47MB）。

もともとは AAC-LC 96kbps を base64 で埋め込んだ単一ファイル構成でした。
2026年11月2日に別ファイル方式へ変えています。アーティファクトの公開共有では
**審査を通る音声形式が MP3 と WAV だけ**で、AAC（`data:audio/mp4`）が弾かれるためです。
WAV を base64 で埋め直すと22kHzモノラルでも約20MBになり、ページの16MB上限を超えます。
画像も JPEG / PNG / GIF / WebP のみ通るので、馬券の透かしの SVG は PNG に変換しました。

副産物として**起動が速くなりました**。曲は必要になった画面で初めて取りに行くので、
最初に落ちてくるのは0.47MBだけです。同じ曲への同時リクエストは `fetchBuf` が束ねます。

代償として、`index.html` を**ローカルで直接ダブルクリックすると音が鳴りません**
（file:// では XHR がCORSで止まる）。サーバー経由か公開URLなら鳴ります。
音を含めて誰かに渡すときは公開URLを使ってください。

macOS には MP3 エンコーダがありません（`afconvert` は MP3 を書き出せない）。
5MBまで小さくしたい場合は ffmpeg か lame の導入が要ります。

| 画面 | 曲 | ループ |
|---|---|---|
| タイトル・馬選択・殿堂・遊びかた | 育成中BGM | ○ |
| 育成（ハイアンドロー〜振り分け） | ハイアンドロー | ○ |
| 出走表 | ファンファーレ001 | **×**（一度きり） |
| レース | レース中BGM＋空気感（重ねる） | ○ |
| レース結果・最終リザルト | リザルトBGM | ○ |
| レース終盤（差し込み） | ゴール歓声 | **×**（一度きり） |
| ハイアンドロー的中 | いえーい | **×** |
| ハイアンドロー失敗 | ああん | **×** |

育成画面はハイアンドローから振り分けまで**一曲を流し続けます**。
途中で曲が変わると、ポイントが確定しただけなのに場面が切り替わったように感じるためです。

`メインBGM.wav` は今回は使っていないので**変換していません**。
使いたくなったら 32kHz モノラル WAV にして `audio/` に置き、`BGM_SRC` に足すだけです。

**ループは Web Audio**（`AudioBufferSourceNode.loop`）に任せています。
`<audio loop>` だと AAC の符号化遅延ぶん曲の切れ目で音が途切れますが、
`AudioBufferSourceNode` ならサンプル単位でつながります。

ただし**音源そのものの末尾に無音が入っていました**ので、そのままループすると
一周ごとに音が消えます。波形を測ると次のとおりでした（WAV 化の際にこの末尾は切り落としてあります。
`_loopEnd()` の判定は残してあるので、無音つきの音源を足しても動きます）。

| 曲 | 長さ | 末尾の無音 | ループ位置 |
|---|---|---|---|
| ハイアンドロー | 32.61秒 | 6.42秒 | 26.46秒 |
| レース中 | 56.39秒 | 6.28秒 | 50.28秒 |
| リザルト | 47.47秒 | 2.82秒 | 44.96秒 |
| 育成中 | 93.54秒 | 2.46秒 | 91.31秒 |

そこで再生開始時に**鳴っている終わりを探して `loopEnd` に入れます**（`BGM._loopEnd`）。
末尾から 20ms ずつさかのぼって RMS が 0.0015 を超える位置を探し、
余韻のぶん 0.15 秒だけ足した地点で折り返します。結果はキャッシュするので毎回は測りません。

### レース中の混ざりかた

レースだけは**2本を重ねます**。場内のざわざわ（空気感・61秒）を敷いて、その上に
レース中BGMを薄く乗せる構成です。

| | 音量 |
|---|---|
| 空気感 | 0.40（`AIR_VOL`） |
| レース中BGM | 0.30（`BGM_VOL.race`） |
| 最終局面の歓声 | 0.30（`CHEER_VOL`） |

曲とは別の**層**として扱うので（`BGM.playLayer` / `stopLayer`）、
ゴール前にレース中BGMが引いても空気感は鳴り続けます。消えるのは結果画面に移るときで、
歓声といっしょに4.5秒かけて落とします。

3本が重なるぶん合計が振り切れないよう、master の後ろに**リミッタ**を1つ挟んでいます
（`DynamicsCompressor`、threshold −2dB / ratio 20）。
実測で普段は作動せず、保険として効きます。

実録の空気感が鳴っている間は、合成の歓声（`Amb`）を**2割強まで引っ込めます**。
同じ役割の音が二重になると濁るためで、蹄音のほうはそのまま残します。

### ゴール歓声の頭出し

ゴール歓声は31秒あり、波形を測ると**10.5秒の一点だけが突出**しています（最大値）。
手前の3.7秒と8.0秒にも小さな歓声が入っていて、そこから鳴らすと
「何度も歓声が上がってから最後に本番」という妙な聞こえ方になりました。

そこで**最高潮の一発だけ**を使います。ゴールの1.8秒前（`CHEER_LEAD`）から、
音源の8.7秒地点を頭出しして鳴らすと、10.5秒の山（`CHEER_PEAK`）がちょうどゴール板に重なります。
手前の歓声（3.7秒と8.0秒）は再生範囲に入りません。

出だしは**1.5秒かけて湧き上がらせます**（`CHEER_FADE`）。
実測で0.3秒47%・0.9秒86%・1.5秒96%・1.8秒98% と、ゴール板でちょうど出しきります。
手前の歓声を避けつつ、唐突に現れないぎりぎりの長さです。

音楽はその少し前、**ゴールの3.2秒前から2.6秒かけて引かせます**（`CHEER_MUSIC_OUT`）。
音が薄くなったところへ歓声が来るので、差し込んだ感じになりません。

4コース・等速/2倍速で数値検証した結果、歓声の山がゴール板に重なる位置は
**10.45〜10.49秒**（狙いは10.5秒）、音楽が引き始めるのはゴールの
**3.13〜3.18秒前**でした。

やっかいなのは、再生速度が一定でないことです。等速・2倍速に加えて、
残り270mからは `FINAL_SLOW` で徐々に減速します。そこで発走時に
**「各フレームから1着ゴールまで、等速なら実時間で何秒か」の累積表**を作っておき
（`G.cumReal`）、実際の残り時間はそこから `rp.speed` で割って出します（`G.realToWin`）。
毎フレーム積分し直す必要がなく、途中で速度を変えても「直線から」で飛ばしても正しく合います。

デコード待ちで数百ミリ秒ずれると台無しなので、**発走時に歓声だけ先読み**しておき
（`BGM.preload`）、さらに鳴らす瞬間にもう一度残り時間を測って
頭出し位置を決めます（`BGM.cue` の offset に関数を渡せるのはこのため）。

音楽を切っているときは歓声も鳴らないので、そのときだけ合成の歓声（`Amb.roar`）を残します。

### 読み上げの直し

合成音声が誤読する語は、読みに置き換えてから渡します（`YOMI` → `yomi()`）。
画面に出る文字は元のままで、読み上げる文字列だけ差し替えます。

| 表記 | 渡す読み | 誤読 |
|---|---|---|
| 好スタート | こうスタート | よしみスタート |
| 馬群 | ばぐん | うまぐん |
| 馬身 | ばしん | （予防） |

「好」も「馬」も、単独に近い形だと訓読みに引っぱられます。
一方で「絶好の手応え」「各馬」「競馬場」のように熟語として馴染んでいれば正しく読まれるので、
そちらは触りません。気になる読みが出たら表に1行足すだけです。

### 短い効果音

ハイアンドローの的中で「いえーい」（音量0.26）、失敗で「ああん」（0.32）が鳴ります（`hlPick`）。
どちらも3秒弱で、デコード済みのまま**常駐させます**（`BGM_KEEP`）。
入れ替え対象に入れると、連続して押したときに読み直しが挟まって間に合わないためです。

**曲の切り替えはクロスフェード**（`BGM._start` が新しい音を立ち上げてから前の音を0.5秒で落とす）。
同じ曲が続く画面では鳴らし続けるので、レース結果→最終リザルトのように画面が変わっても
リザルトBGMは途切れません。

**音量は曲ごと**に決めています（`BGM_VOL`）。レース中だけ 0.17 とかなり低いのは、
実況の音声・歓声・蹄音が同時に鳴るためで、「なんとなく鳴っている」程度に留めています。さらに**実況がしゃべっている間は
自動で3割まで下げます**（`BGM.duck`。`Amb.duck` と同じタイミングで呼ぶ）。

**デコード済みは3曲まで**（`BGM_CACHE_MAX`）。1曲ぶんの PCM が30MB前後あるので、
6曲すべて持つとスマホでは重すぎます。追い出された曲は次に使うときデコードし直しますが、
前の曲を鳴らしたままデコードしてから切り替えるので、音が途切れることはありません。

**最初のタップまで鳴りません。** ブラウザの自動再生制限で、ユーザー操作の前に
AudioContext を動かせないためです。起動時に `pointerdown` を拾って
`AudioContext.resume()` し、そのとき表示している画面の曲を鳴らします。

この `pointerdown` は**外しません**。アプリを離れて戻ると AudioContext が
止まったままになることがあり、一度きりの解除だと二度と鳴らなくなるためです。
`visibilitychange` でも戻ったときに `BGM.resume()` を呼びます。

右上の **♪ ボタン**でいつでも入切でき、設定は localStorage に残ります
（`sankan_bgm`）。実況音声の入切（レース画面の 🔊）とは独立です。

## 馬名について

ライバル馬の名前は、**歴代GI出走馬をもじった架空馬135頭**のプール（`MOJIRI_NAMES`）から引いています。
1960年代から2020年代まで各世代を網羅していて、出走表が本物のレースカードのように読めます。

実名そのものは使っていません。法的な整理は次のとおりです。

- **競走馬名にパブリシティ権はない** — ギャロップレーサー事件（最高裁 平成16年2月13日判決）で、
  馬主が競走馬名の無断利用を差し止める権利は認められないと判断されています
- 残る論点は**商標**だけで、問題になるのは「商品の出所を示す使い方」をしたとき。
  18頭のうちの一頭としてゲーム内に出るのは商標的使用にあたらない可能性が高く、低リスク
- ただし**アプリのタイトル・ストアの紹介文・アイコンに使うのは商標的使用**にあたるので避けること

この線引き（競馬場＝実名／レース名＝仮名／馬名＝もじり、いずれもゲーム内限定）を保つのが安全です。
公開前には一度専門家に確認することをおすすめします。

## 音声実況

実況テロップはブラウザ内蔵の音声合成（Web Speech API）で読み上げます。
**外部サービスも音声ファイルも使わない**ので、1ファイルのまま・オフラインで動きます。

- 声は Hattori → O-Ren → Otoya → Kyoko の順に、あれば使います（いずれも端末内蔵）
- 読み上げ速度は2倍速で1.45倍、ゴール前は0.92倍に落として緊迫感を出します
- 新しい実況が入ったら前の読み上げは中断します（実況なので常に最新を優先）
- テロップ右のスピーカーでオン/オフ。設定は保存されます
- iOSは最初のタップで音声を解錠する処理を入れてあります

実況は**馬番呼び**です。架空のカタカナ名は読み間違えられることがあるのに対し、
数字は確実に正しく発音され、短く切れるので実況のリズムが作れます。
勝ち馬だけはゴールで馬名も読み上げます。

## ハイアンドロー画面

## 初期能力の抽選

初期能力は固定値ではなく、脚質ごとの範囲から**1頭ごとに抽選**されます。

| 脚質 | 走力 | パワー | スタミナ | 器用さ |
|---|---|---|---|---|
| 逃げ | 46〜62 | 29〜43 | 38〜54 | 27〜41 |
| 先行 | 27〜41 | 38〜54 | 29〜43 | 46〜62 |
| 差し | 29〜43 | 46〜62 | 38〜54 | 27〜41 |

中心値は従来の固定値と同じなので、**平均バランスは変わりません**（素質合計の平均170.0）。

**分布**（`rollStat`、重み ＝（半幅＋1−中心からの距離）の3乗）

| 中心からのずれ | 0 | ±1 | ±2 | ±3 | ±4 | ±5以上 |
|---|---|---|---|---|---|---|
| 確率（幅±8の場合） | 22% | 各15% | 各10% | 各6% | 各4% | 各2%以下 |

中心±1に約55%、±2に約75%が入り、端は1%未満です。

**見せ方**：馬選択では範囲だけを表示し（バーの金の線が中心）、
抽選結果は**育成の振り分け画面**の「この馬の能力」で開示します。

```
                初期値      現在
走力             D 56   →   A 82
パワー           F 31   →   D 58
スタミナ         E 46   →   C 66
器用さ           F 33   →   E 49
合計              166   →    255
```

左が抽選で決まった初期値、右が現在の能力です。右の値は**いま振り分けている分も含めて
その場で動く**ので、＋を押すと表が伸びていきます。等級（ABC）も併記し、
伸びた能力は金色にしています。2走目以降も同じ表が出るので、
「どこから来てどこまで来たか」が常に見えます。

以前は中心値からのズレを「上振れ +3」「大はずれ −5」とラベルで出していましたが、
情報が多いわりに判断には使えなかったので外しました。

**素質が三冠率に与える影響**（各8000回）

| 素質合計 | 三冠率 |
|---|---|
| 〜162（下振れ） | 13.6% |
| 163〜166 | 12.6% |
| 167〜173（標準） | 20.0% |
| 174〜177 | 27.1% |
| 178〜（上振れ） | 32.8% |

抽選を入れると三冠が3連勝を要するぶん平均が下がるため、

## バランス（検証済みの数値）

シミュレーションを数千回まわして調整しています。

育成は **ハイアンドロー → 振り分け** の2ステップです。元手は **固定12 ＋ 前走の着順ボーナス**。

**ラウンド数は 3 → 2 → 1 と減ります**（三冠達成後の最終調整は1回）。
レースが進むほどハイアンドローの比重が下がり、代わりに前走の着順が成長の中心になります。

**着順ボーナス**（次の育成の元手に上乗せ）：1着 +24 ／ 2・3着 +13 ／ 4・5着 +7

**連勝倍率は `1.0 / 1.2 / 1.4 / 1.5 / 1.5`** です（`HL_MULT`）。
以前は `1.0 / 1.2 / 1.5 / 2.0 / 2.5` でしたが、4連・5連まで押し込んだときだけ
突き抜けた馬ができてしまうため、上限を 1.5 に抑えました。

**三冠達成率（遊び方別・各1500〜1600回）**

| 遊び方 | 育成の獲得(1/2/3回目) | 1走目 | 2走目 | 3走目 | 三冠 | 四冠 |
|---|---|---|---|---|---|---|
| 博打（薄いほうに賭ける） | 16 / 19 / 16 | 11% | 7% | 6% | 4.0% | 2.5% |
| 安全運転（2連で降りる） | 30 / 35 / 26 | 26% | 19% | 19% | 9.5% | 3.7% |
| 標準（3連で降りる） | 35 / 39 / 30 | 32% | 28% | 32% | **15.4%** | 8.9% |
| 攻め（4連で降りる） | 37 / 40 / 31 | 36% | 33% | 37% | **20.6%** | 12.3% |
| 深追い（5連で降りる） | 35 / 39 / 30 | 34% | 30% | 35% | 19.8% | 13.1% |
| 降りない | 12 / 16 / 13 | 6% | 1% | 0% | 0.1% | 0% |

**倍率を変えた効果**（同じ計測器で新旧を比較）

| 遊び方 | 旧倍率の三冠率 | 新倍率の三冠率 |
|---|---|---|
| 標準（3連） | 16.8% | 15.4% |
| 攻め（4連） | 24.1% | 20.6% |
| 深追い（5連） | 26.9% | **19.8%** |

浅く遊ぶぶんにはほとんど変わらず、**深く押し込んだときだけ効きます**。
旧倍率では「5連まで押す」が最良（26.9%）でしたが、いまは4連が頂点で、
それ以上は押しても損になります。引き際の判断が意味を持つようになりました。

### 4能力の効き方

**どの能力も同じくらい効き、コースによって順位が入れ替わる**ように調整しています。
合計を固定したまま1つの能力だけ +24 したときの勝率です（差し馬・各400回）。

| コース | 走力 | パワー | スタミナ | 器用さ | 画面のヒント |
|---|---|---|---|---|---|
| 早月賞 中山2000 | **38%** | 26% | 22% | 34% | 走力 ＞ 器用さ ＞ パワー |
| 日本クラウン 東京2400 | **50%** | 25% | 29% | 31% | 走力 ＞ 器用さ ＞ スタミナ |
| 菊華賞 京都3000 | 36% | 22% | **53%** | 16% | スタミナ ≫ 走力 ＞ パワー |

測り方：各能力を `(RIVAL_POWER[コース]+29)/4` で割り付け、1つだけ +24、残り3つを −8
（合計は固定）。差し馬・各600〜800回。2026年11月2日の位置取り改修後に測り直した値です。
`buildField` は毎回ランダムなので、300回程度では順位が入れ替わります。600回以上で測ってください。

3コースとも**ヒストと実測の順位が一致**しています。小回りで4コーナーの中山は器用さ、
直線526mの東京は走力、3000mの京都はスタミナ。コースの性格がそのまま出ます。

以前は**スタミナがどのコースでも突出**していて（早月賞で 走力21/パワー19/スタミナ51/器用さ13）、
ヒントに従うと最弱の馬ができる状態でした。原因は能力のスケールの差です。

| 能力 | 旧 | 新 |
|---|---|---|
| 走力 | vmax に +1.65 m/s（0→100で**2.3%**） | +2.30 m/s（`vBase` を下げて中央値は据え置き） |
| スタミナ | 脚が切れると **−22%**（−3.8 m/s） | **−17.5%** |
| 器用さ | コーナーで `2.90-2.50×能力` | `4.50-5.20×能力`（差が2倍） |
| パワー | 坂 `1.00-0.85×能力`／末脚 `2.60` | 坂 `1.00-1.20×能力`／末脚 `3.20` |

走力の幅が狭すぎ、スタミナ切れの罰だけが桁違いだったのが原因でした。

**着差**（同格の馬で200回ずつ実測）

| レース | 1着→2着 | →8着 | →18着 |
|---|---|---|---|
| 早月賞 | 1.7馬身 | 7.0 | 17.6 |
| 菊華賞 | 2.5馬身 | 9.8 | 20.1 |

馬群は走行中に「平均速度からのズレ」を**約1/3に圧縮**しています（`K.packTight`）。
能力差と運を同じ比率で縮めているので**着順の確率は変わらず、着差だけが実際の競馬に近づきます**。
圧倒的に強い馬が弱い相手を倒した場合は10馬身以上離れます。

### 早月賞の難易度（2026年11月3日・実測）

早月賞は三冠で**最短なのに上り坂がいちばん多く**（2000mのうち671mが0.3%超）、
コーナー負荷も最大です。走力で押し切るだけでは足りず器用さとパワーが要る、というヒントは
形状どおりです。

**人気とオッズ**（各3,000回・`makeOdds` のみ）

| 自馬 | 1番人気率 | 単勝の中央値 |
|---|---|---|
| 初期値のまま(170) | 0.0% | 62.3 |
| 元手12だけ(182) | 0.0% | 26.6 |
| 走力に全部振る(205) | 99.7% | 2.3 |
| 4能力に均等(205) | 25.6% | 5.6 |

`makeOdds` は 2000m では走力×1.00・パワー×0.62・器用さ×0.58・スタミナ×0.42 で評価します。
**同じ合計205でも、走力に寄せた馬は1番人気になり、均等に振った馬は4番人気あたりになります**。

**不利の表示が出すぎている**

`meRes.hadTrouble` が立つ確率は、合計208で 逃げ81% / 先行93% / **差し98%**。
カンストした差し馬でも91%です。`K.troubleRate=0.0022` は1レースあたり平均3〜4回起きる値で、
「道中で不利があった」が**ほぼ毎回出る**ため特別な出来事として読めません。
カンスト時に助言を出さないようにはしましたが、頻度そのものを下げる余地があります。

**他の三冠との比較**（同じ馬で4レース・各660回）

| 馬 | 早月賞 | 日本クラウン | 菊華賞 | 有真記念 |
|---|---|---|---|---|
| 合計208・逃げ | 51.5% | 0.0%（平均13.3着） | 0.0%（18着） | 0.0%（18着） |
| 合計240・逃げ | 99.8% | 48.6% | 0.0%（17.0着） | 0.0%（18着） |
| カンスト400・差し | 100% | 100% | 100% | 99.7% |

`RIVAL_POWER` の刻み（181→223→275→約358）が1回の育成で得られる30〜40点より大きいので、
**早月賞は四つの中で明確にいちばん易しく**、同じ馬のままでは次のレースで勝負にならない作りです。

### 差し馬の脚づかい

差し馬は `pace:[0.942, 0.952, 0.964, 1.010, 1.055]`、`lateMul:1.65` です。
道中は後方で脚をため、4コーナー手前から位置を上げ、直線で一気に伸びます。

**自分が差し馬のときの平均順位**（中山2000m・100回・同格より少し強い馬）

| 地点 | 25% | 50% | 75% | 90% | 97% | 着順 |
|---|---|---|---|---|---|---|
| 平均順位 | 10.4 | 10.9 | 7.2 | 1.8 | 1.0 | 1.0 |

半ばまでは中団から後ろ、残り500m付近から動き出し、直線で先頭に立つ形です。

**脚質ごとの三冠率**（各800回・能力を均等に振った場合）

| 脚質 | 能力調整前 | 調整後 |
|---|---|---|
| 逃げ | 12.9% | **20.1%** |
| 先行 | — | **17.8%** |
| 差し | 26.1% | **22.6%** |

差し一強だったのが、3脚質とも18〜23%に収まりました（ばらつき4.8ポイント）。
あわせて `RIVAL_POWER` を 175/217/269 → **181/223/275** に上げ、
逃げ馬の末脚 `lateMul` を 0.80→0.98、差し馬を 1.65→1.40 にしています。

### 直線だけ圧縮を緩める

圧縮は位置の入れ替わりも一緒に潰してしまいます。そのままだと差し馬が後方から動けず、
「道中ずっと後ろにいて、そのまま終わる」だけの脚質になっていました。

そこで**残り420mから圧縮を 0.33 → 0.50 へ緩めます**（`K.tightFrom` / `K.tightEnd`）。
道中は一団のまま、最後だけ脚色の差が位置に出ます。

着差への影響は**後方だけ**に出ます（早月賞で 1着→2着 1.8馬身は変わらず、1着→18着が 18.8 → 21.0）。
競り合いの見え方は変えずに、縦長になるのは離された馬だけです。

**出遅れ率**（器用さで決まる。出遅れると時間を失い、さらに追走でスタミナを余計に使う）

| 器用さ | F35 | E45 | D55 | C65 | B75 | A85 | S95 |
|---|---|---|---|---|---|---|---|
| 出遅れ率 | 30.0% | 20.1% | 12.4% | 6.8% | 3.0% | 0.9% | 0.1% |

**有真記念には毎年この4頭が招待されます**（`ARIMA_GUESTS`）。
チョーシンフジタ／テンサイバケンシ／マジシャンミズノ／サスガニステーキ。

脚質・強さ・枠順は毎回ランダムですが、**常に上位を争う格**になるよう
他馬より強く設定してあります（`GUEST_MIN`〜`GUEST_MAX`）。

| | 平均着順 | 3着内 | 5着内 |
|---|---|---|---|
| 招待馬1頭あたり | 5.7〜6.3着 | 30〜37% | 48〜56% |

上位5着のうち**平均2.1〜2.5頭が招待馬**です（ランダムな馬なら1.1頭の計算なので約2倍）。
招待馬を強くしたぶん他の13頭を弱くしているので、プレイヤー側の難易度は変わりません。

**全能力99以上の完成馬は必ず1着になります**（`isPerfectHorse`）。
内部ではその馬が勝つまでレースを引き直しているので、着差は自然なままです。

**有真記念だけは相手が三冠馬の格に応じて決まります**。
三冠馬の能力合計は328〜400と幅があり、固定の強さでは弱い三冠馬が惨敗してしまうためです。
傾きは1未満なので、強い馬ほど有利になります。

| 挑む三冠馬 | 平均着順 | 勝率 | 3着内 |
|---|---|---|---|
| 合計328（最低級） | 6.0着 | 6% | 27% |
| 合計336（AAAA） | 4.8着 | 14% | 41% |
| 合計352（SASA） | 3.5着 | 30% | 57% |
| 合計375（中央値） | 2.0着 | 58% | 84% |
| 合計400（オールS） | 1.2着 | 83% | 99% |

**能力の効き**（1項目を +25 したときのタイム短縮）

| | 走力 | パワー | スタミナ | 器用さ |
|---|---|---|---|---|
| 早月賞 | 2.0s | 1.2s | 0.5s | 1.2s |
| 日本クラウン | 2.5s | 1.0s | 0.8s | 1.2s |
| 菊華賞 | 2.8s | 1.8s | **3.8s** | 1.4s |
| 有真記念 | 2.6s | 1.4s | 1.0s | **1.8s** |

**菊花賞（菊華賞）前の能力**：標準プレイで合計約300。能力を尖らせて振れば A や S が2つ並びます。

## 能力が上限に達したとき

全能力が100になると、それ以上は振り分けられません（画面に「全能力が上限に達しました」と出ます）。

**振りようがなくて余ったポイントは、最終スコアに加算されます**（`G.spare` → `calcScore` の `spare`）。
重みは**1ポイント＝12点**で、能力1と同じです。こうするとカンストしても損得が出ず、
上振れを引いて育成が決まったぶんがそのままスコアに乗ります。

カンストしている間は**ハイアンドローの画面にも**
「全能力が上限に達しています／余ったポイントは、最終スコアに加算されます。」と出ます。
そうでないと、上限に届いたあとのハイアンドローが無意味な作業に見えてしまうためです。

ただし**自分の意思で残したぶんは対象外**です。まだ振る余地があるのに
「このまま進む」で残したポイントは消えます。加算されるのは `allocRoom()` が 0 のときだけで、
わざと振らずにスコアを稼ぐ抜け道にはなりません。

**ポイントを余らせたまま進むこともできます。** ボタンは常に「出走へ進む」で、
余りがある状態で押すと「ポイントが N 余っています。このまま次へ進んでいいですか？」と
一度だけ確かめます（`finishAllocAsk` → `tr.confirmLeft`）。
温存はできない（持ち越されない）ので実質的には損ですが、止めるほどのことでもないと判断しました。
上限に達していて振りようがない場合は、確認せずそのまま進みます。

## 調整したいとき

| 変えたいもの | 場所 |
|---|---|
| 難易度（ライバルの強さ） | `RIVAL_POWER` — 数字を上げると難しくなる |
| 出走馬の力量差 | `RIVAL_JIT`（±の幅。上げるとオッズも広がる） |
| ハイアンドローの配点 | `HL_PTS`（的中数ごとの素点）と `HL_MULT`（連勝倍率） |
| 育成の元手（固定値） | `BASE_POINTS`（既定12） |
| 着順ボーナス | `RANK_BONUS` |
| 育成ごとのラウンド数 | `HL_ROUNDS`（既定 `[3,2,1]`） |
| 脚質の初期能力 | `STYLES[*].base` |
| 賞金 | `COURSES[*].prize`（万円単位） |
| レース1本の再生時間 | `RACE_SECONDS`（既定42秒。2倍速で半分） |
| 走路に映す範囲 | `renderRace` 内の `span`（小さいほど寄る） |
| 直線のカメラ固定区間 | `FINAL_SPAN`（既定155m） |
| ゴール前のスロー | `FINAL_SLOW`（既定0.45倍） |
| 位置どり（内／外） | `baseLane` と `updateLanes` |
| ゴール後に走り続ける秒数 | `RUN_OUT`（既定2.2秒） |
| 実況の声・速度 | `pickVoice`（声の優先順）と `G.say`（速度・高さ） |
| 歓声・蹄音の音量 | `Amb.update`（進行度と寄りで決まる） |
| 実況の文面 | `G.buildTelop` の `say`（読み上げ）と `msg`（画面表示） |
| 有真記念の招待馬 | `ARIMA_GUESTS`（名前）／`GUEST_MIN`・`GUEST_MAX`（強さの幅） |
| ライバルの馬名 | `MOJIRI_NAMES`（135頭。足すだけで増やせます） |
| 着差の詰まり具合 | `K.packTight`（小さいほど着差が詰まる。着順の確率は変わらない） |
| 直線での入れ替わりやすさ | `K.tightFrom`（緩め始める残り距離）と `K.tightEnd`（直線での圧縮率） |
| 差し馬の動き出し | `STYLES.sashi.pace`（区間ごとの脚の使い方）と `lateMul`（直線の伸び） |
| 出遅れ率 | `K.gateP`（F時の確率）と `K.gateExp`（カーブの鋭さ） |
| 馬群の追走 | `K.chaseGain` / `K.chaseMax` / `K.chaseEnd`（追走が消える残り距離） |
| 有真記念の相手 | `ARIMA_BASE` / `ARIMA_SLOPE` / `ARIMA_MIN` / `ARIMA_MAX` |
| 走りの物理 | `K`（最高速・スタミナ・坂・コーナー・末脚など） |

`K` を触ると勝ちタイムがずれます。コースごとの基準タイムは `COURSES[*].vScale` で合わせてください。
